## 2. What “reproducible” must mean in this audit

Keep maintenance state, scientific outcome, and reproduction evidence separate.
`archived`, `measured_negative`, and `execution_verified` answer different
questions. A failed method can be reproducible; an active method can still have
missing provenance. An unrun idea has no historical score to reproduce.

## 5. Reproduction audit execution plan

### A. Preserve identities and build the inventory

1. Freeze an audit input SHA, current refs, remote heads, worktree states and
   protected experiment source SHAs. Preserve all 100 original method records.
2. Create protected archive refs and a verified Git bundle outside the checkout
   before any history rewrite. A bundle must retain **all relevant refs**, not
   just HEAD. Trial-restore it and verify the refs and required objects.
3. Separately inventory ignored data/checkpoints/results, local site files,
   Slurm logs and job source archives. A Git bundle does not contain those assets.
4. For each method/campaign, record: lifecycle, original outcome, settings,
   source ref, command/environment, required inputs, result locations,
   availability/hash status, strongest completed reproduction check, and gap.
   Reuse the existing method inventory as the key; do not create a competing
   scientific status catalogue.

**Pass condition:** no branch-only history or result dependency is silently
omitted. Missing historical artifacts are listed explicitly, with recovery
versus regeneration distinguished.

### B. Complete the active result/weight inventory on CPU

The expected active training set is **2 histories × 3 seeds × 5 roles = 30
continuation checkpoints**, plus the two shared B3/B5 foundations. The five
roles are ERM, X22, mixed X14, X17-25%, and X17-50%. The expected continuation
evaluation set is **90 setting/seed/role/year summaries**, each containing four
scenarios. Frozen foundations have six setting/year summaries; do not invent
three separately trained foundations from reference reuse.

Check named paths and compact records first. In allocated CPU work, verify
file sizes/hashes and cross-record identities, then inspect checkpoint metadata
only for required trusted assets. Do not recursively scan all of `/scratch`
or load unrelated archived weights. Check actual sample/target identities,
not just the counts 3181/2856/2102. Keep the training-year normalization and
the evaluation corruption configuration tied to each comparison.

**Pass condition:** all required rows are either verified or have a concrete
missing/provenance gap. No blanket “reproducible” status from file existence.

### C. Repair and validate reconstruction paths on CPU

Fix the collector's snapshot-provenance issue first. Run affected command,
checkpoint-identity, route-composition and paper-aggregation tests in a CPU
allocation. Exercise collection through the actual `submit.sh` archive context.
Reconstruct both clean-route variants and X22+X14 from existing summaries;
check full coverage, duplicate rejection and every derived AP reference.

Use the preserved paper ZIP for a standalone extraction/rebuild check with
original run paths unavailable. Figure PNG equality is meaningful in the
matched environment; PDFs/ZIPs may contain timestamps and need not have equal
bytes across new builds. Require matching numerical data, labels and layout.
Store new evidence under a new output directory; never overwrite frozen v2.

**Pass condition:** declared inputs suffice for the selected rebuild mode,
all expected cells are present, and source references remain resolvable.

### D. Reevaluate saved checkpoints before retraining

With a separately authorized GPU budget, start with one matched T1/seed-0
set, checking current entrypoint compatibility and fixed-checkpoint predictions.
Use the same split, corruption settings, sample ordering, batch semantics and
normalization as the historical evaluations. Agree the metric/prediction
tolerance from a deterministic repeat check before seeing candidate deviations;
do not import the old diagnostic's `4.3e-6` discrepancy as a universal tolerance.

Extend to T5 and remaining years/seeds only when the first checks resolve
compatibility. Account for 90 continuation evaluations and six frozen-reference
evaluations if full active coverage is requested. Do not silently count an old
2021 summary as a fresh reevaluation.

**Pass condition:** the complete requested matrix is reproduced within the
predeclared tolerance, or each mismatch has an identified cause. A missing
original checkpoint blocks historical replay; training a replacement creates
a new experiment identity.

### E. Full training and clean-room reconstruction, if required

First retrain one five-role matched set from the preserved foundation with
3000 optimizer steps and physical/effective batch 64. Progress to both histories
and three seeds only after this resolves the training question. A complete
continuation rerun means 30 trainings (90,000 nominal optimizer steps across
models), plus evaluations; it is a materially different scope from CPU auditing.

Rebuilding B3/B5 introduces foundation variability and must be reported
separately from rerunning continuations from the original foundations. A full
new-server test also needs public download, conversion, repair, assembly,
training-only statistics and environment installation from declared sources.
The original and WSTS+ archives are both needed. No bitwise-identical training
or unchanged score is promised across hardware/software changes.

Archived methods receive availability/provenance and reconstruction audits by
default. Runtime checks are selected by execution family or an actual defect;
full retraining of an archived direction requires an explicit scientific reason.

**Pass condition:** a dated report distinguishes result reconstruction, fixed
checkpoint replay, continuation retraining and fresh foundation/data rebuilding.
Negative/invalid/unrun outcomes remain intact even when their code executes.

### Resource and stopping boundaries

This request authorizes planning and inspection, not submitting the stages
above. The previous uncapped allowance concerned paper-material preparation;
it is not an implicit new training campaign. No new Slurm work was launched.

For the next CPU stage, a reasonable proposed initial envelope is two sequential
jobs: a 2-CPU/4-GiB/30-minute reconstruction check and a 4-CPU/8-GiB/60-minute
bounded artifact audit. Confirm against the discovered input sizes before
submission; no automatic retries or scope expansion. GPU smoke/replay and full
training receive separate limits after actual checkpoint availability and
per-role timing are known. An evidence gap stops the dependent stage, not the
independent source/documentation audit.

### Rewrite procedure and acceptance

1. Freeze/protect original refs and trial-restore the all-refs backup. Capture
   both published state and the local-only branch tips. Do not run GC/pruning.
2. Build the proposed series on a separate review branch/worktree, with one
   logical behavior plus its tests/docs per commit. Keep the audit/fix work
   separate from history-only rearrangement.
3. Record an old-to-new mapping. Splits and squashes are many-to-many mappings,
   with action, rationale, protected original ref and evidence anchors; a new
   SHA is an editorial source organization, not the SHA an old job executed.
4. For a history-only rewrite, require identical final tracked trees against
   the frozen baseline. Review the series with `git range-diff` and final
   `git diff`; tree identity alone does not certify sensible intermediate
   commits. Handle the original merge separately instead of flattening it.
5. Check each proposed logical boundary for absent imports, missing configs,
   broken recipes, source/generated-page mismatch and tests dependent on later
   commits. Execute only relevant numerical/model checks through Slurm.
6. Keep old job archives, raw results and original provenance unchanged.
   Improvements or new reproduction results are separate additive commits.
7. Prefer publishing a separate curated branch and retaining main as the
   scientific record. Replacing published main or force-pushing is a separate
   final decision after the mapping, protected refs and validation are reviewable.
   No history rewrite or push is performed by this plan.

## 7. Completion checklist and order

The working order is **preserve sources/assets → inventory gaps → repair and
validate reconstruction → organize navigation → construct reviewed commit
groups → consider GPU replay/training separately**. Do not start by rebasing the
only copy of the evidence history.

The audit is complete when:

- Every inventory entry has an explicit reproduction scope and evidence/gap,
  without altering its original scientific outcome or reactivating archives.
- All 30 active continuation assets and the 90+6 evaluation records are either
  verified or explicitly missing, with exact source and input identities.
- The standard archive-based collector path is tested and both material build
  modes have declared dependencies and reproducible inputs.
- Directory ownership/navigation is clear, stable imports still work, and
  no raw data, checkpoint, original result or branch-only source is lost.
- Proposed split/squash groups have dependency checks and an old/new mapping;
  final tree equivalence and restored original refs are verified.
- The final report states which checks were performed, which historical
  checks were reused, which runtime/training stages remain unexecuted, and
  whether anything was actually published.
